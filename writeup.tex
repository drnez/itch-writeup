\section{Introduction}

\subsection{Background}

In this section, I will set out some key terms and definitions, and explain some crucial concepts, knowledge of which form prerequisites to the rest of the write-up. This is intended mostly towards readers will little knowledge about modern Linux systems.

\subsubsection{Linux}

\textbf{Linux}, while sometimes referred to as an operating system, like macOS and Windows, is in fact just a kernel. A \textbf{kernel} is, in simple terms, the core of an operating system, dealing with the CPU, and allocating memory to processes, among other essential operations. However, on its own, it does not provide a functional system, and is certainly not an operating system itself \cite{LinuxAndGnu}.

An operating system is a collection of software that provides a usable system to an end user. Therefore, the Linux kernel is often distributed along with large amounts of other software, in the form of a Linux \textbf{distribution}. There are hundreds, if not thousands, of such distributions, examples including Ubuntu, Debian, and Arch Linux. When I refer to a \textbf{Linux system}, this is not in reference to the Linux kernel, but rather a full operating system built on top of the kernel.

\subsubsection{Package managers} \label{PackageManagerS}

All computer systems need software to function, so there must be a mechanism for users to install software. At its core, \textbf{software} is simply code, that is \textbf{compiled} ("translated") to a binary format that can be executed by the processor. Installing software, in its most basic form, just consists of copying those binary files to a location where the system recognises them as executable programs.

For Windows systems, most software comes with a dedicated installer (and uninstaller), which carries out this process for the application. However, this is very rarely the case on Linux systems. Software is often released as just source code, and the user is responsible for the installation.

Manual installation is not particularly difficult (the code simply needs to be downloaded, compiled, tested, then copied into place), however this can get tedious when repeated for hundreds of programs. Furthermore, this makes uninstallation very difficult, as there is no way to know which files were installed by which program, and dependency management becomes near impossible.

\textbf{Dependencies} are software or libraries that are required for a program to be installed. There are also \textbf{conflicts} between software, where two programs cannot be simultaneously installed on a system. Often, these occur between versions of packages. 

For example, where $p$ denotes a package, $p_a$ may require $p_c$ with version $\geq 3.0$, and $p_b$ may conflict with $p_c$ versions $\geq 3.5$. This means that for $p_a, p_b, p_c$ to be simultaneously installed, $p_c$ must have version $v$, where $3.0 \leq v < 3.5$.

Therefore, one of the defining features of a Linux distribution is the package manager they include. \textbf{Package managers} can perform all the tasks above, and more. Very often they have access to a repository of trusted and popular software, so the user can install, uninstall, and update software with just one command. For example, the following command in Arch Linux installs the web browser, Firefox:

\begin{lstlisting}[language=bash,     literate={\#}{{\textbf{\#}}}1
           {\$}{{\textbf{\$}}}1,
]
    # pacman -S firefox
\end{lstlisting}

Here, pacman - the package manager for Arch Linux \cite{ArchWikiPacman} - gets the \textit{package} for Firefox from its public repository, and then copies the required files into place, keeping records of what files it installed and where. This incredible ease of use is a massive draw towards Linux, and specifically existing Linux distributions.

\subsubsection{Linux From Scratch}

\textbf{Linux From Scratch (LFS)} is a project that provides an online, continuously updated, book with instructions on how to build a Linux system yourself, compiling and installing all software manually from source code \cite{LFSHome}, and not using any of the provided distributions - the vast majority of which come with some form of installer.

\subsection{Motivation} \label{MotivationSS}

Having recently installed a Linux From Scratch system, there is a clear gap for a package manager, which is not provided in the book. This is intentional, to bring the user's attention to compiling and installing the base software from scratch \cite{LFSPkgMgt}. However, this is not sustainable if the system is to become usable long-term.

An advanced, practically usable system will at some point need complex software packages, including but certainly not limited to graphical toolchains, programming frameworks, and desktop environments. These come with many dependencies, shared libraries, and version conflicts.

Even without such large packages, as a system grows, so will the number of packages (even smaller ones) it has, which feed into the same issues. There are also problems associated with upgrading software, where all files relating to the old version need to be cleanly uninstalled, and replaced with the new version, without breaking the dependencies of any other currently installed software \cite{LFSPkgMgt}. It is not sustainable to continue without a well-defined package manager at this point.

This drives users into three main groups:
\begin{enumerate}
    \item They create a basic, personal package manager to suit their needs.
    \item They install another distribution's package manager, such as Gentoo's Portage, or Arch's pacman \cite{GitHubLfsPacman}.
    \item They leave their LFS system as-is after installation, never using it for any practical purpose, rather leaving it as a completed educational experience.
\end{enumerate}

All three of these come with significant, non-trivial downsides.

In the first case, these package managers tend to be simple and limited in scope, and while their creation does provide a good educational experience, they are often not capable of fully supporting a growing system.

Plus, programming ability is not a prerequisite to building an LFS system, so, while a minority, there are users who are capable of installing such a system, but not creating a package manager for it. While there are no formal studies on the proportion of Linux users who are not programmers, online discussions seem to suggest the existence of a notable minority \cite{RedditLinuxNonProg}.

The second case has the benefit of providing a highly reliable, popular, and documented package manager, often with all the user's needed features and more. However, there are two key downsides here.

Firstly, this in effect turns the user's LFS system into a version of the distribution providing the package manager, eliminates many of the purposes of LFS, which is about creating and maintaining your own system, with full control over all software installed. The sheer complexity of these package managers removes such control from the users, and while it does often produce a working system, the user has in effect just followed a very long path to installing that distribution.

Secondly, and perhaps most crucially, these package managers have been specifically designed for their own distribution, and an LFS system is by definition different. These systems may handle certain cases differently, or have different directory structures, among other subtle differences. Since the package manager has not been made for, and is not commonly used with, LFS systems, there tends to be a lack of support, with a very small user base that can help with any issues that will eventually arise.

For these reasons, I came to the decision to write a package manager, dedicated to Linux From Scratch systems, addressing all the shortfalls identified.

\section{Design}

\subsection{Non-technical aims} \label{AimsSS}

At the very start of the project, I established that the most basic level of success for the package manager can be determined by whether it can install and remove packages. This is trivial to test - I just need to install a sample of packages, verify that they work correctly, then remove them, and verify that they are no longer present on the system.

However, it is not particularly challenging to create such a package manager, and many already exist. Therefore, the following aims will act as my criteria for establishing a more sophisticated level of success for the project. Almost all of them stem from Aim \ref{TargetLFS}, the need to target Linux From Scratch users and systems, since the problem I am aiming to solve with this project is the lack of a suitable package management solution for Linux From Scratch users, as established in Section \ref{MotivationSS}.

These criteria will also be used to guide the development process, ensuring the artefact created fits my goals as closely as possible.

\begin{enumerate}
    \item It must be targeted towards LFS systems. While it should ideally be usable on most Linux systems, decisions should be guided by what is needed on an LFS system, and what the LFS user base would prefer. \label{TargetLFS}
    \item The compilation ("building") of software should be left to the user, meaning precompiled binaries should never be distributed. Linux From Scratch is based on the principles of compiling ones own software, and this is a key requirement if a package manager is to be used by LFS users. \label{NoPrecompiled}
    \item Users should be able to patch and modify source code as they desire prior to installation, with the package manager placing no restriction on this. \label{AllowPatching}
    \item The compiled software should be stored as \textit{packages} of some form for future use, so that the user does not have to rebuild software to reinstall it. Note that this does not defy Aim \ref{NoPrecompiled}, since these packages will have been compiled by the user themselves, configured as they desire, rather than externally compiled, then distributed. \label{StorePkgs}
    \item There should be no central server the package manager needs to interact with to function. It should be able to run wholly locally, with no limitations. \label{NoServer}
    \item It must provide a method for full and clean uninstallation, removing all traces of the software, while not affecting any other programs. \label{UninstallPkgs}
    \item Dependencies and conflicts must be tracked and managed appropriately, as a key purpose of this project. \label{TrackDeps}
    \item It must not simply be a derivative of an existing package manager - there must be something unique about it, or a non-trivial reason to use it instead of another existing package manager. This has been partially addressed in Section \ref{MotivationSS}, but it should be continuously thought about. \label{BeOriginal}
\end{enumerate}

Aims \ref{TargetLFS} and \ref{BeOriginal} need to be tested qualitatively, with a personal judgement being used to establish whether they have been successful. This should be apparent when comparing the functionality of this package manager to other, existing ones, especially to do with the design decisions that have been made.

Aims \ref{NoServer} and \ref{TrackDeps} need to be tested by examining the source code I have produced, and ensuring the functionality conforms to their specifications.

The other aims can all be tested objectively, by attempting to use the functions they describe on the package manager for a sample of different packages. They will be classed as successful at the end of the project if those functions work for all packages tested.

These aims are not completely independent of each other, and should not be though of as such. Instead, they build on and complement each other. For example, allowing users to compile packages allows them to patch their source code as well. Aim \ref{BeOriginal}, the need to be original, in some ways derives from Aim \ref{TargetLFS}, since aiming the package manager specifically towards Linux From Scratch users is something that has not been done before in a complete, distributable package manager. Further, most of the aims contribute towards meeting Aim \ref{TargetLFS}, since they are part of what targets this package manager for LFS specifically.

I chose the name \textit{Itch} for this package manager to reflect the importance of Aim \ref{TargetLFS}, since it is being built for Linux From \textit{Scratch}.

\subsection{Package maintenance}

Through my research of existing package managers, I have identified three promising methods employed by package managers to install and subsequently uninstall packages. These generally all provide some method to track what files are installed, and where, so that they can be removed on uninstallation.

These are generally independent of the method for dependency resolution, which will be discussed in Section \ref{DependencySS}.

\subsubsection{Modifying destdir} \label{DestdirSSS}

This method is used by many package managers made for commerical Linux distributions, such as pacman \cite{ArchWikiPacman}. This is a very simple method, consisting of configuring the package to be installed in the correct, final, location, but modifying the DESTDIR environment variable upon installation, so that the package is instead placed in a "fake" location where it will not function properly \cite{FakerootLFS}.

From there, an archiving utility, often tar, is used to create an archive of the files in this fake directory. This archive is then unpacked in the correct installation location, installing the software as normal. However, now the archive still exits, and within it, it holds a copy of every file that was installed, and where they were placed. This makes uninstallation very simple, as these files are simply iterated over and deleted \cite{qpkg}.

\subsubsection{Using unionfs}

This is a unique approach to package management, and follows the same basic principles as the fake installation location method, but differs greatly in implementation \cite{UnionfsLFS}.

The current file system is accessed read only, and a new, empty, file system is created, which can be written to. A union between these two is made using the unionfs utility. Therefore, when the package is installed to the union, the union will contain the new state of the system, with the new package installed, and the previously empty file system will contain all of the installed files.

These can then be stored in some format, providing all of the files installed by the package for easy uninstallation. Once the user is happy, the union file system can be copied to the main file system (that was previously accessed read only). This allows easy rollbacks in case of an error mid-install.

The main benefit this has over the DESTDIR method is that files are \textbf{forced} to be installed in the empty file system, while a poorly packaged program may ignore the DESTDIR environment variable. However, this is rare, and seems to be more of a theoretical advantage rather than a practical one.

\subsubsection{Functional package managers}

Functional package managers have been gaining popularity in recent years, and they are based on the principle that all configuration and instructions given to packages must be stored in one central file.

This file is then hashed, and that hash corresponds to the unique state of the system \cite{TryNix}. This is very useful for creating reproducible builds, and makes debugging much simpler since a configuration can be recreated on another device with ease.

While this is a fascinating concept, I made the decision not to research it much further, since these package managers do not fit within my fundamental aims for \textit{Itch}, which is to complement a Linux From Scratch system, simplifying tasks. This would be introducing a whole new paradigm, and users would be much better served installing an existing, developed, functional package manager if they want a system like this, such as Nix.

\subsubsection{Conclusion}

Although the unionfs method was fascinating from a technical point of view, I decided to use the DESTDIR method over unionfs. The main reasons were that it is much better documented in case any problems arise, it is much simpler to understand and debug, particularly for users of the program who should ideally understand how it works in full, and the unionfs method did not provide any significant advantages over the DESTDIR method, despite the added complexity.

\subsection{Dependency resolution} \label{DependencySS}

Now, I must consider the problem of dependency resolution. Each package can depend on, or conflict with, certain other packages, meaning certain packages must be installed with each other, while other packages cannot coexist on a system. To make this more complex, these are most often bounded by versions. See Section \ref{PackageManagerS} for a deeper explanation.

This means that package managers must come with a method to \textit{resolve} dependencies, meaning to find what packages - and in what versions - need to be installed on the system for a new package to be added.

Dependency resolution is an NP-complete problem \cite{DependenciesFormal}, meaning in practical terms that it cannot reliably be solved "quickly" (there is no known polynomial time solution). Therefore, shortcuts and optimisations are often taking to make it tractable.

\subsubsection{Maintaining a curated repository}

The vast majority of popular Linux distributions employ this method, where the maintainers of the distribution maintain an online repository, containing one version of each package available, ensuring that those versions all work together. This greatly simplifies the problem of dependency resolution, since package versions are no longer a concern.

Another reason this method is very commonly used in more mainstream distributions is that the package set becomes universal among systems of the same version, making problems easier to diagnose and debug.

Moreover, this fits very well with the philosophies of some distributions. For example, Arch Linux operates on a rolling-release model, always using the very newest software, so this curated repository only contains the newest usable builds \cite{ArchMain}. On the opposite end of the spectrum, Debian focuses on stability, so a curated selection of tested, mature packages enables the creation of very robust systems \cite{DebianUsability}.

However, this does not at all fit within the Linux From Scratch philosophy, which is about users creating their own system as they please. \textit{Itch} is simply intended to be a tool to help users with this, and therefore it should not limit the range of software users can install, or curate package repositories based on release version. This choice should be fully in the hands of the user.

Furthermore, since this relies on an online repository of curated software, it violates Aim \ref{NoServer}.

\subsubsection{Holding a package database}

Another method consists of holding a database with the required dependency information for a number of packages (available in many versions). This differs from the curated repository method, in which one version of each package is stored which will work with each other. 

This allows the user to choose what packages they install, and with what version. Gentoo operates a similar system, using an \textit{ebuild} repository, which contains \textit{ebuild} files with the metadata of packages \cite{GentooEbuild} - most of which have multiple available versions.

However, it does require than an online database to be maintained, violating Aim \ref{NoServer}. While this can be mitigated, by allowing users to build their own database (keeping the database in a human-readable format), and by allowing the file to be downloaded once and repeatedly used, meaning the package manager does not need to interact with an online sever every time it runs, it still does violate the spirit of the aim, preventing the package manager being from functioning wholly locally.

\subsubsection{Using placeholders}

The problem with not holding any form of package database is that the system has no information about packages that could satisfy dependencies. Consider a system (using the notation $p_x-y$ to refer to package $x$, version $y$) where, the installed packages are $\{p_a-3.0, \; p_b-1.2\}$, and $p_c-2.0$ is to be installed. However, $p_c-2.0$ requires $p_a-v>3.5$ and $p_d-v\le1.0$. Now, the system does not know about what packages exist within those ranges, and whether they depend on any other packages, or conflict with any existing packages. This makes dependency management very difficult. 

In this case, placeholders can be used, meaning the resolver would simply output the version ranges that a satisfying package must fit into. However, this is a one-way relationship. Where the set $S$ is a satisfying set of packages, and $S_p$ output of the program involving placeholders,
\begin{equation}
    S \implies S_p, \quad S_p \centernot\implies S.
\end{equation}
This is because the dependency information of those packages in the range is not known, nor is the actual package versions within the range. 

This does not result in a useful package manager. For large packages with hundreds of (often nested) dependencies, it creates a very arduous path for the user.

Imagine a package $p_e-4.2.1$ is to be installed, and the package manager identifies that it requires $p_e-2.0.0<v\le3.2.0$. Trying to install that, the package manager can only then inform the user that it requires $p_f$. However, the version of $p_f$ the user chose to install ends up conflicting with $p_b-2.0$, which is installed on the system. The system will have no method to detect these in advance, while a system with a package database would instantly output a satisfying arrangement, if one is available.

Very often, this method will be more time-consuming and frustrating than handling the dependencies yourself, or finding a satisfying arrangement online.

\subsubsection{Conclusion}

This is a tough situation, where either Aim \ref{NoServer} must be (at least partially) defied, or the dependency resolver produced will not be practically usable.

I can immediately remove the first option, of maintaining a curated repository, since that goes too far against the purpose of a Linux From Scratch package manager (Aim \ref{TargetLFS}), and in effect creates a new distribution. The third option of using placeholders is also not reasonable, since it creates a borderline unusable program. 

Therefore, I have no option but to hold a package database, containing just the dependency information for packages. This will be in a form that can be downloaded once, and extended by users. This database can start with data scraped from other package manager databases, and extended with user contributions. 

However, since this does go against the concept I originally had for the package manager, I have decided it would be best to split the package \textit{installer} (the installation and uninstallation components) and the dependency resolver into separate projects. They will still work with each other as a unified package management system, but they should also be capable of working independently, and in conjunction with other package management tools. 

Besides the obvious benefit of the package installer component not relying on an external database, this also better follows the Unix philosophy, where each program should complete just one task well \cite{UnixPhilosophy}. It is also more useful for users who only require one half of the system, and use a different method for either dependency resolution or package installation and removal. 

\section{Programming the package installer}

\subsection{Basic installation}

The principles of building an installing software can be boiled down to the following steps: (patch), configure, build, (test), install. Since \textit{Itch} is focused on ensuring users still compiling their own code (Aim \ref{NoPrecompiled}), and allowing patching as desired (Aim \ref{AllowPatching}), it will not interfere with any of these steps until \textit{install}.

To make this clear to the user, I created procedures for \textit{configure}, and \textit{install}:

\begin{lstlisting}[language=bash]
    install_prefix="$HOME/prog/school/epq/dest/"

    configure() {
        echo "configure as normal, ensuring the following is added:"
        echo "    --prefix=$install_prefix"
    }

    build() {
        echo "make as normal"
    }
\end{lstlisting}

This also reminds the user to specify the install prefix - the location the software will be once fully installed - to the configure command. It is currently set to a location within my home directory to allow for testing without risk of damaging my system, but this will be changed to /usr (the default prefix for LFS systems), with a configuration file allowing it to be changed, once the development is complete.

The code below performs the installation, with a method similar to that described in Section \ref{DestdirSSS}.

\begin{lstlisting}[language=bash]
    temp_dir="/tmp/itch/build"

    install() {
        rm -rf "$temp_dir" # in case not properly cleaned before
        mkdir -p $temp_dir

        make DESTDIR="$temp_dir" install # install in temp dir

        findname

        sudo mkdir -p "$pkgpath"

        sudo tar czf "$itchpkgpath" -C "$temp_dir$install_prefix" .

        installpkg
    }

    installpkg() { # existing tarball in pkgpath
        cd $install_prefix

        # finds existing files that will be overwritten
        for file in $(tar tzf "$itchpkgpath" | grep -v '/$'); do
            if [ -e "$file" ]; then
                printf "Overwrites '%s'\n" "${file#./}"
            fi
        done

        read -p "Proceed? (yes/NO): " confirmation

        if [ "$confirmation" = "yes" ] || [ "$confirmation" = "y" ]; then
            tar xf "$itchpkgpath"
        else
            echo "Aborted!"
        fi

        rm -rf "$temp_dir"
    }
\end{lstlisting}

The following process is followed by the code above to install packages:
\begin{enumerate}
    \item A temporary installation directory is created in /tmp/itch/build, and the package is installed there first. This directory is placed in /tmp as it is "made available for programs that require temporary files" \cite{FHS}.
    \item The tar archive \cite{GnuTar} (a gzipped tarball) of the files to be installed is stored in /var/lib/itch/pkgs/\{package name\}/\{package name\}.itchpkg. This both allows the package to be reinstalled without recompilation (Aim \ref{StorePkgs}), and holds the data about files created during installation. It is located in /var as "/var contains variable data files" \cite{FHS}, and these files are updated while the program runs.
    \item The files to be installed are compared with any files already installed, finding the files that will be overwritten, so the user can cancel the installation if that would be problematic. The for loop for this was heavily inspired by qpkg's \cite{qpkg} verify function \cite{qpkgCode}.
    \item The tarball is unpacked in the final installation directory, completing the installation, and the temporary build directory is removed.
\end{enumerate}

The following procedure determines the name of the package being installed, by either using the name of the current directory, or the parent directory if currently inside a build directory. Since this is not fully robust, the user has the chance to override its output.

\begin{lstlisting}[language=bash]
    findname() {
        pkgname=$(basename "$(pwd)")

        # tries to find package name (either current dir or parent if in build dir)
        if [ "$pkgname" = "build" ]; then
            pkgname=$(basename "$(dirname "$(pwd)")")
        fi

        echo "Enter package name (blank for [$pkgname]):"
        read input

        if [ "$input" != "" ]; then
            pkgname="$input"
        fi
    }
\end{lstlisting}

A switch statement calls the required procedure based on the flags the user passes into the program.

\begin{lstlisting}[language=bash]
    case "$1" in
        "-c")
            configure ;;
        "-b")
            build ;;
        "-i")
            if [ -z "$2" ]; then
                install
            else
                getname "$@"
                installpkg
            fi ;;
        *)
            echo "Error!"
            ;;
    esac
\end{lstlisting}

The installpkg procedure is called directly if the name of a package that has already been compiled by the user is specified, skipping the building stage. In this case, the getname procedure is called, setting variable based on the name of the package provided, and ensuring it is valid.

\begin{lstlisting}[language=bash]
    getname() {
        pkgname="$2"

        pkgpath="/var/lib/itch/pkgs/$pkgname"
        itchpkgpath="$pkgpath/$pkgname.itchpkg"

        if [ ! -f "$itchpkgpath" ]; then
            echo "Error!"
            exit
        fi
    }
\end{lstlisting}

\subsection{Tracking file ownership}

Currently, the uninstall method will just consist of deleting all the files that were installed by a package. This brings about a problem: some files are provided by multiple packages. These should not be deleted upon the removal of one package that provided them if another package that also provided them is still installed.

There is also a second, though less significant, problem in the removal of directories. These should only be removed if they will be empty once all files to be deleted are removed, to prevent another program's files residing in the same directory being deleted. The approach qpkg takes is simply not deleting directories \cite{qpkg}, and while this still works, it is not very elegant.

Both problems can be solved by tracking which packages provide each file.

I chose to use gdbm \cite{gdbmManual} for the database holding this information. It provides a quick, lightweight, NoSQL method to retrieve data, and is already installed in a default LFS system \cite{gdbmLFS}.

The pkgfiles array is populated inside install, and this updateshared procedure is called just prior to final installation in the final directory.

\begin{lstlisting}[language=bash]
    updateshared() {
        shareddir="/var/lib/itch/shared"
        dbdir="$shareddir/files.gdbm"

        # create dir and file if not already existing
        sudo mkdir -p "$shareddir"
        sudo touch "$dbdir"

        for file in ${pkgfiles[@]}; do
            gdbmout=$(echo "fetch $file" | sudo gdbmtool "$dbdir" 2>/dev/null)

            echo "store $file \"$gdbmout $pkgname\"" | sudo gdbmtool "$dbdir"
        done
    }
\end{lstlisting}

This uses gdbmtool (a command line interface to gdbm) to add the name of the installed package onto the list of packages that provide a certain file. This table maps each installed file (the key) to this list (the value).

The database is located at /var/lib/itch/shared/files.gdbm. It is in a "shared" directory to show that this file is used by all packages.

However, upon testing, it would take minutes for this procedure to run for larger packages. This was since every time gdbmtool is called (twice per file), the database is opened and closed, and while the actual reading and writing is very quick, this overhead greatly slowed down the process.

Therefore, I replaced this procedure with a short python script - updatedb.py - performing the same task.

\begin{lstlisting}[language=python]
    import sys
    import dbm.gnu

    dbdir = sys.argv[1]
    pkgname = sys.argv[2]

    db = dbm.gnu.open(dbdir, 'c');

    for i in range(3, len(sys.argv)):
        file = sys.argv[i]

        gdbmout = db.get(file)

        if gdbmout is not None:
            pkgs = gdbmout.decode().split(' ')
        else:
            pkgs = []

        # don't add pkgname if already existing - eg for reinstallations
        if pkgname not in pkgs:
            pkgs.append(pkgname)

        db[file] = " ".join(pkgs)

    db.close()
\end{lstlisting}

Python - unlike bash, which is only used for scripting - provides a well-documented interface to gdbm \cite{gdbmPython} such that the database can be opened once at the start of the program, and only closed at the end. This greatly reduced the time taken to update the database to milliseconds, from minutes.

This script is executed from inside the main bash file as follows:

\begin{lstlisting}[language=bash]
    printf "%s" "${pkgfiles[@]}"
        | sudo python "$pythonupdatedir" "$filedbdir" "$pkgname"
\end{lstlisting}

The location of the database and package name are passed to it as command line arguments, while the package files are piped into it, as otherwise the number of files would often exceed the maximum length of command line arguments.

\subsection{Uninstalling packages}

The only reason such lengths have been taken to install packages, rather than simply issuing the installation command
\begin{lstlisting}[language=bash,     literate={\#}{{\textbf{\#}}}1
           {\$}{{\textbf{\$}}}1,
]
    # sudo make install
\end{lstlisting}
is to ensure that these packages can be cleanly uninstalled, leaving no traces behind that could cause problems for other packages, or newer versions of the same package.

Before attempting to uninstall a package, it must first be verified that it is installed in the first place. The contents of /var/lib/itch/pkgs/ cannot be used for this, as they simply contain all archives that have been created. One may have been created but not installed, or installed but later uninstalled. The .itchpkg archives persist here intentionally, to allow easier installation again, but this does mean another method for tracking installed \textit{packages} (not files) is needed.

I decided to also use gdbm for this, linking each package to its installed version.

\begin{lstlisting}[language=bash]
    echo "store $pkgname_name $pkgname_version"
        | sudo gdbmtool "$pkgdbdir" 2>/dev/null
\end{lstlisting}

This does not require a separate python script, as the database is only accessed once per package installed.

The database is stored in /var/lib/itch/shared/pkgs.gdbm, again because this is shared between all packages.

\begin{lstlisting}[language=bash]
    shareddir="/var/lib/itch/shared"
    pkgdbdir="$shareddir/pkgs.gdbm"
\end{lstlisting}

Arch Linux's pacman stores this data in the form of a tarball containing each package as a directory \cite{ArchWikiPacman}, however I chose to use this gdbm database instead since the hashing provided, and not needing to unpack the archive every time, makes it quicker to check whether a package is installed.

Having built this database, I then wrote the uninstallation procedure. A python script is used here as it allows the database to be opened just one time, have the operations performed, and then be closed, rather than opening and closing the database each time as would happen had I just used bash. This translates into a very significant (around tenfold in my testing) time saving.

\begin{lstlisting}[language=bash]
    uninstall() {
        gdbmout="$(echo "fetch $pkgname" | sudo gdbmtool "$pkgdbdir" 2>/dev/null)"

        if [ "$gdbmout" = "" ]; then
            echo "Error! Package not installed to begin with!"
            exit
        fi

        pkgfiles="$(tar tzf "$itchpkgpath")"

        toremove="$(printf "%s" "${pkgfiles[@]}"
            | sudo python
                "$pythonuninstalldir" "$filedbdir" "$pkgname" "$itchpkgpath")"

        echo "$toremove"

        IFS=$'\n' read -rd '' -a toremovearr <<< "$toremove"

        for file in "${toremovearr[@]}"; do
            echo "$file"
            sudo rm -rf "$installprefix/$file"
        done

        pkgname_name="${pkgname%%-[0-9]*}"
        echo "delete $pkgname_name" | sudo gdbmtool "$pkgdbdir" 2>/dev/null
    }
\end{lstlisting}

After confirming that the package is installed, the package's files are taken from the .itchpkg archive made in /var/lib/itch/pkgs/\{pakage name\} during installation. At this point, the python script uninstalldb.py is executed.

\begin{lstlisting}[language=python]
    import sys
    import dbm.gnu

    dbdir = sys.argv[1]
    pkgname = sys.argv[2]
    itchpkgpath = sys.argv[3]

    pkgfiles = [line.strip() for line in sys.stdin]

    db = dbm.gnu.open(dbdir, 'c');

    for file in pkgfiles:
        gdbmout = db.get(file)

        if gdbmout is not None:
            pkgs = gdbmout.decode().split(' ')
        else: # must have been an error
            pkgs = []
            continue

        pkgs.remove(pkgname)

        if len(pkgs) == 0:
            print(file)
            del db[file]
        else:
            db[file] = " ".join(pkgs)

    db.close()
\end{lstlisting}

This opens the files.gdbm database, and removes all occurrences of package being uninstalled. It also prints any files that were only provided by this package, so they can be captured by the main bash procedure, and deletes those entries from the database.

These files that are returned are then all deleted, and the package is removed from the pkgs.gdbm database, as it is no longer installed.

\section{Programming the dependency resolver}

\subsection{Storing metadata} \label{ResolverMetadataSS}

As previously established, there needs to be a database with multiple versions of each available package, storing dependency information. Here, I will specify the format in which this is stored.

Firstly, there will be a gdbm database linking each package name with its available versions (/var/lib/itch-resolver/global.gdbm).

The data for each of these package and version is stored in the general directory: /var/lib/itch-resolver/pkgs/\{package name\}/\{package version\}. This directory will contain three files: conflicts.itch, depends.itch, and provides.itch.

Together, these three files contain all the required information to resolve dependencies and output a combination of packages that all will work together. This format is easy to parse in a program, and as compact as possible, minimising the storage size needed while holding all of the necessary information.

\subsubsection{conflicts.itch}

Each line of this file is in the format:

\begin{lstlisting}
{conflicting package name} {lowest conflicting version} {highest conflicting version}
\end{lstlisting}

The lowest version can be 0, and highest can be left out if not applicable.

These are the packages and versions that cannot be installed together with this package.

\subsubsection{depends.itch}

This has a very similar format. Each package that is required for the target package has a line in the format:

\begin{lstlisting}
{required package name} {lowest version required} {highest acceptable version}
\end{lstlisting}

\subsubsection{provides.itch}

This stores programs that are provided by a certain package, and may be required by other packages. This file has the even simpler format:

\begin{lstlisting}
{provided program name} {provided program version}
\end{lstlisting}

No range is required as each package version provides can only provide another package in one version.

\subsection{Defining the SAT problem}

A dependency resolution problem is expressed as a set of constraints: one package requires another to run, two package versions cannot co-exist, a certain package must be newer than a given version to support a specific version of another package.

These can be encoded as a boolean satisfiability (SAT) problem. This is clear, since both the SAT problem, and dependency resolution, are NP-complete, meaning they reduce to each other in at most polynomial time \cite{DependenciesFormal}. This is useful, since there exists programs called SAT solvers, which are highly optimised to compute large SAT problems.

Therefore, by encoding all the dependency constraints into conjunctive normal form (CNF - the format accepted by SAT solvers), the problem can be given to a SAT solver to find a satisfying arrangement of packages.

I will pass this generated CNF to MiniSAT \cite{MiniSATPaper}, a popular, powerful but lightweight SAT solver with a well-documented shell interface \cite{MiniSATGuide}.

The following rules will be encoded \cite{DepsToCNF}:

\begin{enumerate}
    \item A package's dependencies must be met, or the package not installed.
    \item None of a package's conflicts should be installed, or the package not installed.
    \item Only one version of any package can be installed.
    \item Each package already installed on the system must remain installed in some version (this does not have to be the current one).
    \item The package being installed should be installed with the given version.
\end{enumerate}

\subsubsection{The format of DIMACS CNF}

CNF, or conjunctive normal form, is a format for expressing a boolean expression, where variables (which can only take true/false values) are expressed in a \textit{conjunction} of \textit{disjunctions}. For a disjunction to evaluate to true, at least one variable inside must be true. For a conjunction to do the same, \textit{every} variable inside it must be true. Practically, this means CNF contains multiple lists of variables, in each of which at least one must be true in a satisfiable state. Variables can also be negated: this means that a false variable maps to true, and vice versa \cite{CNF}.

MiniSAT takes input of a CNF file in DIMACS format. DIMACS is a file format for representing CNF, where each line contains a list of integers (which correspond to the boolean variables in disjunction), with the lines in the file are in conjunction together. A negative integer encodes the negation of a variable. All lines must also end with an 0, but this is not a problem variable.

\subsection{Generating a CNF file}

First, we must create a mapping between each package-version and an integer, which will represent the package in the DIMACS file.

\begin{lstlisting}[language=python]
count = 1
for pkg in pkgs:
    versions = global_db[pkg.decode()].decode().split()

    for version in versions:
        pkg_to_num[pkg.decode(), version] = str(count)
        num_to_pkg[count] = (pkg.decode(), version)

        count += 1

    set_provides(pkg.decode(), version)
\end{lstlisting}

The provides data for the packages were also read and stored in this loop, so that they are finished before the conflicts are encoded (if $p_a$ conflicts with $p_b$, and $p_c$ provides $p_b$, then $p_a$ also conflicts with $p_c$, but there is no way of knowing this before the provides data has been encoded.

At this point, we can also encode the dependency and conflict information for the packages.

\begin{lstlisting}[language=python]
for pkg in pkgs: # needs second loop so mappings (and provides) are complete!
    versions = global_db[pkg.decode()].decode().split()

    for version in versions:
        encode_deps(pkg.decode(), version)
        encode_conflicts(pkg.decode(), version)

    # encode "only one version of each package"
    for i in range(0, len(versions)):
        for j in range(i+1, len(versions)):
            sat_clauses.append("-" + pkg_to_num[pkg.decode(), versions[i]] +  " "
                             + "-" + pkg_to_num[pkg.decode(), versions[j]] + " 0")
\end{lstlisting}

Then, the required clauses for local packages are installed, ensuring the packages that are installed remain installed in some version.

\begin{lstlisting}[language=python]
local_pkgs_db = dbm.gnu.open(local_pkgs_db_dir, 'c')
local_pkgs = local_pkgs_db.keys()

full_closure = set()

for pkg in local_pkgs:
    # encode "each package installed should be installed (but whatever version)"
    versions = global_db[pkg.decode()].decode().split() # all available versions

    new_clause = ""
    for version in versions:
        new_clause += pkg_to_num[pkg.decode(), version] + " "

        full_closure.update(get_closure(pkg.decode(), version)) # get closure of each installed/installable pkg-ver
    new_clause += "0"
    
    sat_clauses.append(new_clause)

full_closure.update(get_closure(new_pkg_name, new_pkg_version))
\end{lstlisting}

Above, these packages are also added to a set representing a closure. This closure is expanded by the get\_closure method to contain every dependency of the local packages, and all dependencies of those dependencies, and the dependencies of those, etc. This is also done for the package being installed.

With these, the program adds negated clauses for all packages that do not appear in the closure, ensuring they are not installed. This fixes an issue that came up during testing, where the SAT solver would arbitrarily define unnecessary packages as true. While this would result in a valid system state, the user should only be prompted to install the dependencies they need, rather than all of the packages that could coexist on their system.

\begin{lstlisting}[language=python]
for pkg_num, (pkg, version) in num_to_pkg.items():
    if (pkg, version) not in full_closure:
        sat_clauses.append("-" + str(pkg_num) + " 0")
\end{lstlisting}

The program terminates by printing all of the SAT clauses to standard output, and storing the mappings of DIMACS integers to packages in the closure in a json file.

\begin{lstlisting}[language=python]
for clause in sat_clauses:
    print(clause)

num_to_pkg_closure = dict()

for (pkg, ver) in full_closure:
    num_to_pkg_closure[pkg_to_num[pkg, ver]] = (pkg, ver)

with open(sys.argv[5], 'w') as file:
    json.dump(num_to_pkg_closure, file)
\end{lstlisting}

\subsection{Full dependency resolution}

The CNF-generating program defined above needs to be integrated with a MiniSAT to perform the actual resolutions and output a list of package-versions to be installed.

\begin{lstlisting}
mkdir -p "$tempdir"

sudo python "$installdir/make-cnf.py" "$pkgsdir/" "$itchdir/" "$1" "$2" "$tempdir/mappings.json" > "$tempdir/output" # inputs are pkg and version
minisat "$tempdir/output" "$tempdir/minisat_out" > /dev/null # don't print sat solver output
(grep -oE '(^| )[0-9]+' "$tempdir/minisat_out" | tr -d ' ') > "$tempdir/positives"

python "$installdir/get-positives.py" "$tempdir/mappings.json" "$tempdir/positives"

rm -rf "$tempdir"
\end{lstlisting}

This bash script redirects the output of the make-cnf script into a temporary output file, passes that file to MiniSAT, which generates a list of all variables (representing packages) and whether they are true or false (representing to be installed or not). This file is trimmed to only include the positive, true, variables (packages to be installed), and this is passed to another python script that uses this list, as well as the json file mapping variables to package-versions, to print the complete list of packages that should be installed on the system to provide a minimal, unproblematic state. That script is below:

\begin{lstlisting}[language=python]
import json
import sys

print("Suggested system state [name, version]:\n")

with open(sys.argv[1], 'r') as file:
    num_to_pkg = json.load(file)

with open(sys.argv[2], 'r') as file:
    for line in file:
        line = line.rstrip() # remove trailing \n

        if line == "0":
            break

        print(num_to_pkg[line])
\end{lstlisting}

Note that all temporary files are placed in a specific directory, which is deleted upon the program's termination, so that unnecessary space is not taken up on the user's system.

\section{The final product}

\subsection{Configuration files} \label{ConfigFileSS}

During development, I hardcoded the file paths of the resources that need to be accessed by the various programs. However, this is not suitable for distribution, as users should be able to modify these variables in one place and have it take effect across all program files, and it is best practice to ensure users do not need to modify source code files.

Therefore, I created two configuration files, one for the installer, and the other for the resolver, holding these values. A typical setup (which is being used on my system) is shown below.

\begin{lstlisting}
installprefix="/usr"
tempdir="/tmp/itch/build"

pkgpath="/var/lib/itch/pkgs"
shareddir="/var/lib/itch/shared"

itchinstallerdir="/usr/lib/itch-installer"
\end{lstlisting}

\begin{lstlisting}
installdir="/usr/lib/itch-resolver"

pkgsdir="/var/lib/itch-resolver"

itchdir="/var/lib/itch"

tempdir="/tmp/itch-resolver"
\end{lstlisting}

These values are loaded by the relevant bash scripts as follows, based on the configuration file needed:
\begin{lstlisting}
source "/etc/itch/itch.conf"
\end{lstlisting}
\begin{lstlisting}
source "/etc/itch/itch-resolver.conf"
\end{lstlisting}

Note that the installprefix is where packages installed by the installer will be located (/usr is the default for Linux From Scratch systems).

Also note that the dependency resolver's configuration file contains an entry for itchdir, the directory where the files of the package installer are contained. This is not required, and if that directory is empty the dependency resolver will simply assume that no packages are currently installed on the system. Otherwise, if it is provided, it allows the dependency resolver to ensure already installed packages do not conflict with the one being installer, and vice-versa.

\subsection{Typical directory tree}

This diagram shows where all of the files associated with both the installer and dependency resolver are to be installed on a typical system. The configuration files allow scope for changing some of these, however this layout follows the Linux Filesystem Hierarchy Standard \cite{FHS} and is therefore recommended.

This clearly shows the separation between the installer and resolver components, since they rely on and use separate directories.

    \centering
    \includegraphics[width=0.5\linewidth]{final/itch-filetree.png}

The package archives, storing installation information for future removal, and providing precompiled archives for reinstallation, are found under /var/lib/itch/pkgs/, and /var/lib/itch/shared/ contains information of the packages currently installed on the system, and the files that are installed (and which package(s) they belong to).

The temporary directory /tmp/itch/build/ is used as the fakeroot location for redirecting the installation of a package, and /tmp/itch-resolver/ stores the temporary files created while the dependency resolver runs.

Finally, /etc/itch/ contains the configuration files for both programs. They are not in the users .config directory, since itch is designed to work system-wide.

\subsection{Installation}

Installation is generally simple, but has to be done separately for the package installer and dependency resolver components. This is by design, so that users can install only one, but not the other, if desired.

As dependencies, both components require Bash, Python 3, and GDBM. Additionally, the dependency resolver requires MiniSAT. MiniSAT is the only dependency that is not installed in a default Linux From Scratch installation.

This software has only been tested on a Linux From Scratch and an Arch Linux system. There is no reason that it should not also work on other distributions, but it is only intended to be used on Linux From Scratch, and so some subtleties of other systems may unexpectedly interact with the programs' functionality.

\section{Conclusion}

\subsection{Extent of success}

At the very start of the project, I established that a basic level of success can be established by the package manager being able to install packages. I have clearly succeeded in this, as shown in Section \ref{ExampleUsageSS} - packages can be installed, uninstalled, and have their dependencies resolved. 

However, this project can only be considered truly successful if it adds something on top of other, existing, package managers. In particular, my goal was to target it specifically for Linux From Scratch users. Based on that goal, I defined eight key non-technical aims, in Section \ref{AimsSS}, to guide the project, and serve as a metric to evaluate it upon completion.

Aims \ref{NoPrecompiled}, \ref{AllowPatching}, \ref{StorePkgs}, and \ref{UninstallPkgs} were to be tested by using the package manager with a range of packages, and ensuring that they work in all cases. An example test is shown in Section \ref{ExampleUsageSS}, and tests on the packages \textit{neovim}, \textit{emacs}, \textit{zsh}, \textit{git}, \textit{pulseaudio}, \textit{perl}, and \textit{minisat} were similarly successful. These are two text editors, a shell, a file-tracking utility, an audio driver, a programming language, and a SAT solver (which is actually the only dependency of \textit{Itch} that is unavailable on a base LFS system). This test sample contained a diverse range of software, with different dependencies, conflicts, packages provided, and installation methods supported. Since \textit{Itch} was successful in all of thee cases, it is safe to consider these aims successful.

Aim \ref{TrackDeps}, concerning the ability of the package manager to resolve dependencies, passed an initial check in the test cases above, where it successfully terminated and provided a list of packages that should be installed on a system with the target package. These system states were always successful in the above tests, allowing the target package to run correctly. I ensured that this was not accidental by also passing specific test cases with "hard" dependency situations (with many dependencies and conflicts between packages) using fake packages added to the test database to manually check whether a correct arrangement is output. These tests were all passed, satisfying me that this aim was also successful.

Aim \ref{NoServer} is the only aim that has not been fully successful. As detailed in Section \ref{DependencySS}, in order to create a usable dependency resolver, some form of dependency database is needed. In the Design section, I established this as one that will be held online, and must be downloaded once. Through the development stage, I realised that it is infeasible to create one wholly myself, since there are thousands of available packages, and currently available package managers, such as Pacman \cite{ArchWikiPacman}, have teams of developers working on maintaining their package databases. Therefore, users can solve this in three ways:
\begin{enumerate}
    \item Creating their own package database,
    \item Using another package manager's database,
    \item Establishing a community \textit{Itch} package database.
\end{enumerate}
The first item is generally infeasible for most users, though many very dedicated Linux From Scratch will be able to do this, particularly if they only use a limited range of packages. The third solution is the ideal method - as I had initially aimed to do - however, it is beyond the scope of this project, and would take far too much time for me to do on my own. Therefore, for testing purposes, I used Debian's package database (Debian is a popular Linux distribution) modified to fit the format established in Section \ref{ResolverMetadataSS}. In the long term, my hope is that I, and other users, can establish a large database to end this reliance.

While I do not believe that Aim \ref{NoServer} has been fully unsuccessful, since users can still make their own database of packages, the dependency resolver and package installer have been separated, and the program just needs the database to be downloaded one time (it does not itself interact with any online resource), it would be disingenuous to mark it as successful, as the most usable version of the dependency resolver relies on some form of externally held database.

Aim \ref{TargetLFS}, the need to target Linux From Scratch systems and users, needs to be judged qualitatively, based on the development process I have undertaken, and how the finished product works. I believe that this has been very successful, as I have taken all possible steps to make \textit{Itch} as suitable as possible for such systems and users. The following are just some of these decisions:
\begin{itemize}
    \item The package manager does not compile any software for the user,
    \item The user can freely patch software,
    \item The user can add any software they desire to the package databases,
    \item The package manager does not interact with any online resources,
    \item The package database can be overridden - or even fully created - by the user,
    \item A fakeroot method is used for installation so that it is simple to understand by users and does not impose any methods of using the system,
    \item There is no curated repository of software versions that are supported - any software in any version that the user wants can be used,
    \item Updates are not mandated - the user can uninstall old versions and install new versions whenever they would like to,
    \item Precompiled binaries are not distributed or even supported,
    \item The only dependency used that is not provided in a basic Linux From Scratch installation is MiniSAT.
\end{itemize}

The final aim, Aim \ref{BeOriginal}, is about there being a reason to use \textit{Itch} specifically instead of any other existing package manager. In some ways, this defines whether the project as a whole has been successful, and something of value created. There is no one feature that has been implemented here that does not individually exist elsewhere, however, it is the specific combination that makes \textit{Itch} unique. It is very specifically targeted to Linux From Scratch systems and users, as demonstrated above, and is a unique solution to the problems those users faced, as established in Section \ref{MotivationSS}. Previously, they would need to either rely on another distribution's package manager - removing much of the control that Linux From Scratch affords a user - or install packages manually, if they did not want to create a basic package manager themselves. These are all impractical, particularly for very large packages such as desktop environments. \textit{Itch} is in effect the solution to all of these problems. It handles the repetitive tasks of package removal and dependency resolution, that users find very difficult in larger systems, while leaving all other functions in the hands of the users, affording them as much control as possible. I am therefore happy to consider this aims, and the project as a whole, successful.

\subsection{Scope for improvement}

The following are examples of functionality that could be implemented in the future to improve the package manager.
\begin{itemize}
    \item Speeding up the dependency resolver: a problem with the package manager right now is that the dependency resolver runs slowly - taking seconds for a task that should ideally take milliseconds. This could be improved upon in two ways. Firstly, I could spend more time tweaking the resolution algorithm, to try and find optimisations that can speed up the process. Secondly, rewriting the resolver in a compiled language such as C or C++ would significantly improve the speed compared to Python that I am using at the moment.
    \item Allowing currently installed packages to be marked as such: while ideal, it is unlikely that users will install this package manager before they have already installed a whole array of other packages manually. Currently, they will have to manually modify the database of installed packages do that \textit{Itch} knows these are installed, and avoids conflicts with them when resolving dependencies for new packages. Although this is likely within the capacity of most Linux From Scratch users, it would be nice to add in functionality to add these in natively, without the user having to deal with the databases themselves.
    \item Introducing functionality to natively allow updating packages could help to make \textit{Itch} easier to use. Updating is currently possible, but it takes two separate commands: one to uninstall the pervious version, and another to install the new version. Implementing a single command to handle both could save users some time.
    \item A method to "export" a file containing details of all packages installed on one system, and another method to install all the packages from that file, would allow users to distribute their created system between devices. On one hand, this could be seen as putting too much functionality into one program, which is against the Unix philosophy \cite{UnixPhilosophy}, but on the other hand, this is a natural extension of a package manager, since packages installed in effect defines a system's state.
    \item Including a guided installer that simplifies the installation process for \textit{Itch} could help to eliminate any errors caused by improper installation, however it is very low priority since this should not pose any sort of challenge to a user that has managed to install a whole Linux From Scratch system.
\end{itemize}

\subsection{Comparison with other package managers}

Here, I will compare \textit{Itch} with two very popular package managers: \textit{Pacman} \cite{ArchWikiPacman}, for the Arch Linux distribution, and \textit{Apt} \cite{AptSource}, for Debian.

\begin{center}
\begin{longtable}{|p{0.22\linewidth}|p{0.21\linewidth}|p{0.21\linewidth}|p{0.25\linewidth}|}
    \hline
    \textbf{Category} & \textbf{Apt} & \textbf{Pacman} & \textbf{Itch} \\
    \hline
    Are precompiled packages distributed? & Yes & Yes & No. The user downloads and compiles source code, and the package manager just takes care of installation. Packages, however, are made from code that the user compiles and installs, for subsequent re-installation. \\
    \hline
    Installation procedure & Extracts the precompiled archive in place & Extracts the precompiled archive in place & Installs packages in a fake directory first, creating an archive of the files to install, before copying them into place \\
    \hline
    Uninstallation procedure & Uses the package archive to remove all files specified & Uses the package archive to remove all files specified & Uses the package archive created during installation to remove all files specified \\
    \hline
    Allows patching source code of packages & No & No & Yes \\
    \hline
    Allows users to compile their own packages & No & No & Yes \\
    \hline
    Package information database & Holds a centrally maintained database & Holds a centrally maintained database & Either a centrally maintained database (to be created) or a user's own database can be used \\
    \hline
    Packages available & Packages in a specific version defined by the version of Debian installed. These are typically older, to maintain stability. & The newest possible version of the package that has been packaged for Arch Linux, providing the newest software at the expense of stability. & Whichever packages the user can find dependency installation for. They can choose older, more stable versions, or brand-new, development versions with no restriction. \\
    \hline
    Updates & Most updates are undertaken as full-system upgrades, with a new Debian version allowing a newer version of all packages. & Updates are undertaken on a rolling basis, forced whenever new packages are being installed, ensuring the newest software is always installed. & Software can be updated, or not updated, as and when the user wishes. There are no specific requirements, giving the user full control. \\
    \hline
    Overall structure & The underlying package installation and dependency resolution is performed by \textit{dpkg}, while \textit{Apt} handles the other maintenance and frontend tasks. & The package management is all handled together by \textit{Pacman}. & \textit{itch-installer} handles the package installation and removal, while \textit{itch-resolver} resolves dependencies. This is a unique method of seperation, allowing users to choose which functionality they feel they would benefit from.\\
    \hline
\end{longtable}
\end{center}
Overall, \textit{Itch} has been designed to leave as much as possible in the hands of the user. The structures of Apt and Pacman define the Debian and Arch Linux operating systems respectively, by imposing a usage structure upon users, whether it be one of upmost stability or modernity. However, \textit{Itch} intentionally avoids these decisions, leaving it to the user to create their own distribution, as the Linux From Scratch project intended. It is unique in allowing users to maintain full control of their systems, while automating some of the most tiresome tasks that previously made the maintenance of a Linux From Scratch system almost infeasible over the long term.
